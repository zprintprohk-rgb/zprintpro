| # | 症狀 | 根因 | 修法 |
|---|------|------|------|
| 1 | `gradient` 計數 14≠13 | 註解含該詞被計入 | 只計資料鍵形式 |

## §4 交付紀律（7 條鐵律）

1. **前後斷言**：改前斷言 `hit==1`（原文存在且唯一）、改後斷言 `hit==0`（確實改掉）
2. **整批中止**：任一條不符預期 → 中止全批，**不放行半套修正**
3. **冪等**：找不到原文 = 可能已套用 → 提供 `--deletions-only` / 明確 skip，不誤報失敗
4. **只改目標範圍**：防「隨機替換污染無關項目」（本案曾把紙袋內文改成貼紙文案）
5. **變體遞進**：第一輪修主體 → 重掃 → 第二輪補變體（本案 22→19→4→0）
6. **改資料前先 dump 真實樣本**（§0.23.2 第 1 條）——正則必須依真樣本寫
7. **不擅自裁決**：涉及客戶可見映射/品牌/§0.0 禁區 → 列 A/B/C + 推薦，交拍板

## §6 判「部署延遲 vs 修復失敗」的雙 marker 法

```
marker A = 早前已驗證生效的改動（如 art-posters「1張起印」）
marker B = 本輪新改動（如 pvc-menus「10 張起印」）

A 生效 + B 殘留  → 站點正常更新中，僅落後最新 commit（部署延遲，非失敗）
A、B 皆殘留/失效 → 站點整體未更新（需查 CF Pages build）
```

**響應有效性三重校驗**：HTTP 200 + 長度下限 + marker 可讀；不合格判 `INVALID`，**絕不計入 0**。

## §7 何時「不改」比「改」正確（本案 3 例）

| 情境 | 表面 | 實情 | 處置 |
|------|------|------|------|
| 貼紙「戶外/可移 100 個起」 | 與真值 10 不符 | **大量檔**（`kind='bulk_tier'`），非 SKU 起訂量 | 標 `APPROVED_BULK_TIERS` |
| 賀卡三場景 50/100 張 | 與賀卡真值 10 不符 | **企業套組定位** vs 個人化定位 | 明文化判定，不改數字 |
| 「本品 100 起、少量急件 10 枚起」 | 掃描器報 found=10 | 我方數字**正確**（分流語義） | 保留，清除歧義表述 |

**教訓**：「數字與真值不符」≠「必須改」——必須先判斷**語境與定位**。

## §8 自進化 4 步 SOP（每次踩坑後）

1. **記錄**：把「錯誤結論 / 真相 / 根因 / 防護」寫入 `error-patterns.md` 新條目
2. **固化**：將防護做成**可執行機制**（斷言/腳本/門童），不只寫文字提醒
3. **驗證**：新機制必須能**重現原錯誤**（若重現不出，機制無效）
4. **登錄**：新門童編號先查 `guard-manifest.json` 的 `maxGuardNumber`，取遞增值
