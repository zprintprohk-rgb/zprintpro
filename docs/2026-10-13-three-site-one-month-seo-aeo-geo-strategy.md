## §5 执行层（deepseek Harness）断跑诊断与错峰结论

### 5.1 断跑根因：不是 DeepSeek 平台问题，是调度层实例卡死

**K3 问：是不是 Harness 平台的问题？不适合做定时任务平台？——证据回答：不是。**

| 证据 | 事实 |
|---|---|
| 同链路了健康车道 | ZP-k3-review（每天 07:10）与 ZP-cron-watchdog（06:43）**同期 Result=0 正常跑完**——同一 dsh Harness、同一 DeepSeek key、同一 wrapper 结构，链路本身健康 |
| 失败形态 | daily-content / gsc-feedback / weekly-meta / monthly-matrix 四条车道 LastTaskResult = **0x800710E0**（调度层拒绝），wrapper 日志自 10-10 00:35 起**连 run start 行都没有**——cmd 根本没被启动，dsh 从未被调用，**与 DeepSeek 平台/余额/模型无关** |
| 机制 | 任务 MultipleInstancesPolicy = **IgnoreNew**：残留 Running 实例不退出 → 后续每次触发直接被拒（10-12 23:48:09 两条车道同秒被拒 = 手动触发也撞同一堵墙）; 现场还有一个 10-10 11:02 起驻留的 node 进程（嫌疑残留，未确证） |
| 触发时刻偏移 | monthly-matrix 06:13 → 14:01 才触发、weekly-meta 23:07 → 23:30 才触发 = 机器繁忙时触发延迟 + 拒绝叠加 |

**结论**：Harness（dsh + DeepSeek）适合做定时任务平台——已稳定跑了一个多月；本次断跑是 Windows 任务实例管理事故，不是平台能力问题。
