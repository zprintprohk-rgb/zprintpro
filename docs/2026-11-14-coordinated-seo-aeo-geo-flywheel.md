### 2.3 为什么不再“每周批量写深层 Blog”

1. 对 30–40 位词，主要瓶颈可能是搜索意图、主承接 URL、内容重复、交易信息与内部竞争；继续增加近似文章会进一步分散信号。
2. 旧 Blog 中未核实价格、认证、时效、统计和退款口径会成为搜索与 AI 答案源，**清理错误答案比新增字数更优先**。
3. Blog 车道今后只接“既有文章的真实信息缺口”任务，一次一篇、写域明确、上游证据齐全；没有信息增益就 `NO_OP`。
4. 海报今晚第一任务只限 `poster-printing-guide` 的 D1／D6 真值修复，不能夹带 JA、贴纸、包装或新标题实验。

每个任务必须包含：

`cluster/query → baseline → owner_lane → upstream_inputs → approval_gate → write_scope → production_deploy → online_verify → retest → retry_at → exit_criteria → learning_status`

## 5. 复测学习与“自进化”边界

### 5.1 允许的学习

1. **证据学习**：保存同一窗口、同一词、同一 URL、同一变更批次与实际部署时间。
2. **状态学习**：从 `BASELINE_CAPTURED_NO_OUTCOME` 迁移到部署待验、可复测、有效、无效或未测出。
3. **任务学习**：weekly／monthly 根据 outcome 再派单；重复 DONE 不重做，同因失败达到阈值后停止自动重试。
4. **资源学习**：首页高展示零点击优先 CTR；连续恶化优先诊断；深位且承接混乱优先整合；季节性词按窗口处理。
5. **缺失学习**：缺 GSC、SERP、部署或商业真值时，系统学会降级为 `NO_CURRENT_BASELINE／SERP_UNAVAILABLE／BLOCKED`，而不是补造答案。

### 5.2 禁止的“伪自进化”

- 自动改写自身 prompt、扩大写域或把 WAITING_K3 变 READY。
- 仅凭位置一天上涨就宣布策略成功，或仅凭下跌就回滚。
- 把多次 NO_OP、wrapper exit 0、手动运行成功当成学习能力或业务成效。
- 在没有实际部署／线上验收的样本上统计“胜率”。
- 自动新增付费 API、模型、云组件或第九条 SEO 车道。

### 5.3 复测判定

| 状态 | 必要证据 | 系统动作 |
|---|---|---|
| EFFECTIVE_PENDING | 有基线、有变更，但无部署或未到窗 | 不评价赢输，保留待验 |
| MEASURABLE | 基线＋单变量＋审批＋部署＋线上断言＋到期窗口 | 进入同口径比较 |
| POSITIVE_SIGNAL | 同口径位置／CTR／承接至少一项改善，其他不显著恶化 | 只称积极信号，继续复测 |
| NO_EFFECT | 到期且无改善 | 停止同法重复，回到诊断 |
| NEGATIVE | 连续窗口恶化且有变更时间关联 | 提出回滚或修正，仍需审批 |
| NOT_MEASURABLE | 多变叠加、缺档、未部署或窗口不足 | 不进入胜率，不自动扩量 |

## 7. 订单自动化：零新增费用可行性独立评估

### 7.1 结论

- **完整 12 周全自动方案：不能承诺零新增费用。**
- **有边界的半自动 PoC：可以不新增付费服务，但本轮只完成可行性评估，没有实现或宣称可运行。**
- 订单自动化是独立业务架构，**不得塞进 SEO 协同队列，也不新增第九条 SEO 定时任务**。

### 7.2 仓库核查发现

1. `package.json` 没有 Playwright／Puppeteer 直接依赖，`scripts/**/*playwright*` 无匹配；lockfile 的可选引用不能证明本机可用。
2. 现有 Supabase migrations 未包含本方案所需 `files／api_keys／review_queue` 新表；真实 `orders` schema 与迁移文件并不完全一致，支付路由还会动态探测列，故线上结构仍未核实。
3. R2 bucket、Queues／异步 PDF 质检、新 API 鉴权与审核台都是新增组件，不是现成免费能力。
4. PayPal／Stripe／Airwallex、IOSS 中介、税务、生产、物流、退款重印和人工审核都存在交易成本或运营人力，不能用“软件不另收订阅费”偷换“全链路零成本”。
5. `$49.9` 商品全包价、运费、DDP、Express、SLA 等仍受实测与 K3 拍板约束；任何 `$49.9/月` 一类费用也不得写成已批准或免费。

### 7.3 零新增费用 PoC 边界

| 环节 | 可复用／零新增费用做法 | 保持人工／不得自动化承诺 |
|---|---|---|
| 需求与文件 | 现有 WhatsApp／邮件接收，本地登记订单与文件元数据 | 文件完整性、隐私授权、最终规格人工确认 |
| PDF 质检 | 本地工具做基础页数／尺寸／字体检查，输出辅助报告 | 人工目检出血、色彩、内容和印刷风险；不宣称自动质检全覆盖 |
| 报价 | 复用现有 quote 能力或 docs 中的试算表；只使用已拍板真值 | 生产、运费、税费、DDP 与最终总价人工确认 |
| 审核 | 现有管理员在本地／预览清单批准或驳回 | 不新建 R2／Queues／审核台，不自动放行生产 |
| 收款 | 复用当前 bank transfer／QR／既有流程 | 支付到账人工核实；不接新支付 API，不承诺零手续费 |
| 生产与物流 | 沿用现有线下下单与跟踪登记 | 生产、重印、退款、运费、关税与 tracking 人工确认 |
| 验收 | 1 个虚拟样例走通登记→检查→人工报价→人工审核流程 | 不用真实客户付款／生产做测试；不称端到端全自动 |

PoC 退出标准：明确人工节点、无未拍板客户可见数字、无新付费依赖、无真实资金或生产副作用、全流程有审计记录。若目标仍是原方案的自动上传、异步质检、支付回推、IOSS 申报和 webhook 全自动，则必须重新做成本与架构拍板。
