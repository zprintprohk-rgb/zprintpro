**协议补遗 10.4 — 线上探针必须限定「目标作用域」；共享布局会污染判据**

**坑（双向都会错）**:
1. **判据过宽（假阳性）**：文章页底部/侧栏会渲染**「相关文章」卡片**——它们是**站内既有内容**。
   若整页文本做断言，别的历史文章里的违规串会被算到你头上。
   实测：Etsy 篇首轮验收报 `❌ Alibaba`，实际来自相关卡片
   `School exercise book printing … (vs Alibaba yellow pages 500+ MOQ)`，**我的正文无竞品名**。
2. **判据过窄（假阴性）**：`meta description` / `og:*` **只存在于 `<head>`**，
   若先「剥掉所有标签再匹配」，这些字段会**被一起剥掉** ⇒ 明明在线却报「缺失」。
   实测：Etsy 篇首轮报 `❌ 缺 no 500-piece minimum`，而该串**就在线上 meta description 里**（154 字符）。

**规则（强制）**:
1. 正文断言必须**限定在目标容器内**：从 `<h1` 起 → 到「相关文章 / Related reading / 関連記事 / View More」之前；
   并加一条**自证**：该作用域必须含**目标自己的特征串**（如自己的 H2），否则说明作用域取错。
2. `meta` / `og` 字段断言**走标签提取**（`<meta name="description" content="...">`），**不得**用剥标签后的文本判。
3. 凡「找不到某串」的结论，先回答两问：**① 该串应在正文还是 head？② 我取的作用域是否覆盖它？**
   —— 与「技术债 9 探针 URL 必须反查」同族：**先自证探针，再怀疑内容**。

**协议补遗 10.3 — `git add` 是「追加」不是「替换」；暂存区必须每次主动清点**

**坑**: `git add -- <file>` **不会把暂存区重置为「只有这些档」**，而是把指定档**追加**进现有索引。
因此只要索引里还残留着他人的在途条目（上一轮 `-A`、上一轮 add、他人误 add），
**下一次提交就会把它们一起带走** —— 与 `-A` 是同一后果，只是更隐蔽。

**事故 (2026-09-19, 本会话连续两次)**:
- 第 1 次: `git add -A src/` ⇒ 混入 MOQ10 会话 17 档；
- 第 2 次: `git add -- scripts/guards/credibility-guard.js`（以为只提交这一档）⇒ 索引里**残留**的
  `moq-price-sync-*.{json,md}` + `scripts/moq10-validate-*.ts` 等 **6 档**被一并带上，
  该次 commit 被门禁拦下（🔴 67，`BRAND_LOCALE_MISMATCH 真值 89`）；
  ⇒ 靠**协议第 2 条**（提交前核 `--name-only`）发现，未造成污染。

**强制流程（每次提交都走，不得凭记忆）**:
```
git diff --cached --name-only          # ① 清点：必须逐档等于本次白名单
git restore --staged -- <白名单外的档>  # ② 剔除非白名单条目（只动索引, 工作区不动）
git diff --cached --name-only          # ③ 复核：计数 = 白名单档数
git commit ...                         # ④ 提交
git show --stat --format='' HEAD       # ⑤ 提交后复查：无陌生档
```
> 判据: **白名单 = 本次任务的产物档**。凡不在白名单内的暂存条目，一律剔除后再提交。
> 剔除非白名单条目**只动索引**（`--staged`），绝不回退他人工作区改动。

**协议补遗 10.1 — 混合档的精准暂存手法（2026-09-19 实测可用）**

当**同一檔内**同时含自己与他人的未提交改动（文件粒度拆分不可能）时，用 **hunk 级精准暂存**：
1. `git diff -- <file>` 取 patch → 逐 `@@` 切 hunk；
2. 只保留**改动行全部匹配本任务特征**（如每行含 `FSC`）的 hunk，其余丢弃；
3. `git apply --cached <过滤后的 patch>` 只把该 hunk 进索引；
4. **暂存后必核**: `git diff --cached -U0` 的每一行 `+`/`-` 都必须匹配本任务特征（非 0 ⇒ 误带，立即 `git reset`）。
   工具: `.hermes/_probe-pb/_stage-fsc-hunks-only.cjs` · 核验: `.hermes/_probe-pb/_verify-staged-only-fsc.cjs`

> ⚠️ 注意 `git apply --cached` 的 `--unidiff-zero` **是布尔旗标, 不能写 `=false`**（实测报错 `option takes no value`）。

**协议补遗 10.2 — 他人 commit 可能「带走」自己的档（对称风险）**

2026-09-19 实测: 对方 commit 时把我 5 个档（`lib/seo.ts` / `CategoryIndustries.tsx` / `HeroBanner.tsx` /
`product-faqs.ts` / `products.ts`）的改动一并带入 ⇒ 我的工作量被拆到两个 commit。
**处置**: 不撤销他人已落 commit（撤销成本高于收益），改为**显式记录**（在交付报告中写明
「本任务 N 档已随他人 commit `<hash>` 进入, 另 M 档在本 commit」），保证可追溯;
此后提交前用 `git status --porcelain` 核「我的档是否已不在未提交列表」以发现该情况。

# ⚠️【置顶·2026-09-19 技术债 10】—— 并发会话协议：禁用 `git add -A`

## 技术债 10 — 批量 stage 禁用 `-A`；并发仓必须**逐档显式 add**

**模式**: `git add -A <dir>` / `git add .` 会**把工作区里所有人的未提交改动一并暂存**。
在多会话（或多车道）并发的仓库里, 这会把**别人的在途工作混进自己的 commit** ——
后果不是「多提交了几行」, 而是:
① 无法追溯谁改的; ② 别人的工作在你不知情下被推上线; ③ 一旦要回滚你的 commit, 会**连带毁掉别人未提交的工作**。

**事故 (2026-09-19, 推送前 3 分钟拦下)**:
- 本会话执行 FSC 写法归一 (20 档), 最后一次图省事用了 `git add -A src/`;
- 该命令把**另一并发会话（MOQ 10 纸品线起订量 100→10 改造）**的 **17 档在途改动**一并提交:
  `src/data/print-method-policy.ts`(新增 `PAPER_GOODS_*` 族) · `src/lib/price-data.generated.ts`(+1,327 行)
  · `src/data/price-tables/*.json` 5 档(+1,483 行) · PDP/services 组件 · `h1-builder.ts` · `seo-keywords.ts` 等;
- **发现方式**: 提交后核对 `git show --stat`, 察觉统计里出现自己没碰过的档;
- **止损**: 该 commit 尚未推送 ⇒ 立即 kill 延迟 push 任务 (`pwsh-43`), 核实远端仍为 `1e0a584b`, 污染未上线;
- **拆分失败**: 同一文件内有**两个会话的行级改动**（`CategoryIndustries.tsx` 同时含
  我的 `FSC certified→FSC-certified` 与其 `100 張起印→10 張起印`）⇒ **文件粒度拆分不可能**,
  回滚我的 commit 会毁掉对方工作 ⇒ 停手上报, 由人裁决。

**并发会话协议（强制, 本仓适用）**:
1. **禁用批量 stage**: 不得使用 `git add -A` / `git add .` / `git add -u`;
   **只能逐档显式 add**（`git add -- <file>` 一行一档）。
2. **提交前核对**: `git diff --cached --name-only` 必须**逐档等于本次任务的档清单**;
   多一档都要停下查来源。
3. **提交后复查**: `git show --stat HEAD` 再核一遍; 发现陌生档立即 `git reset --soft HEAD~1`（**保留改动**）并上报。
4. **推送前核查**: `git fetch` + `git log origin/main..main` 确认待推 commit 集合 = 自己的产出;
   并核 `git ls-remote origin refs/heads/main`（唯一可信远端头判据）。
5. **作业前查并发**: 开工先看 (a) `.hermes/locks/lane.lock`; (b) `git status` 是否有**非自己产出**的未提交改动;
   (c) `C:\Users\Administrator\.dsh\sessions\--F-zprintpro-nextjs--` 下最近 mtime 的会话数
   （>1 表示有人手会话并发）。
6. **并行任务的改动必须由该任务自己 commit**: 不得代提交他人的在途工作;
   必要时**停手上报**（本事故即如此处置）。

**与既有规则的呼应**: §0.35.5「人手会话与 lane 并发改同一文件 = 9/19 撞车事故」是同一族问题的**车道版**;
本条是**人手/多会话版**, 两者共同构成「并发写入防护」。

# ⚠️【置顶·2026-09-19 技术债 9】—— 探针 URL 必须从**数据实际键名**反查

## 技术债 9 — 线上探针的 URL 靠「猜 slug」⇒ 404 被当成「内容缺失」

**模式**: 线上验收探针若**手写 slug**（凭记忆/推断拼 URL）, 拼错时页面返回 **404**;

**事故 (2026-09-19 波 1/2/3 线上验收)**:

- 首轮结果 **FAIL 3**, 全部是**探针自身**问题, 与线上内容无关

**规则 (强制)**:
1. 探针 URL **禁止手写/推断** —— 必须从**数据实际顶层键名**反查（本次新增

3. 凡「阳性对照失败」, **先自证探针 URL 是否 200**, 再怀疑内容。

# ⚠️【置顶·2026-09-19 技术债 8】—— 批量替换必须排除「注释行」

## 技术债 8 — 单字级替换会污染**代码注释**（注释不在门童扫描面内, 却承载语义）

**模式**: 门童 #4 双向化**只扫字符串字面量值**（注释行被 `common.isCommentLine` 排除）。
因此注释里的中文/简体**从来不是待清理目标**; 但**字级/词级全局替换**（如 `层`→`層`、`标`→`標`、`卖点`→`売りポイント`、`选购指南`→`選び方指南`）
会**无差别命中注释行**, 把内部工作记录与代码注释改坏 —— 而门童**不会报错、不会计数**, 属完全静默的副作用。

**事故 (2026-09-19 波 4)**:
- 规则 `层`→`層`、`标`→`標`、`卖点`→`売りポイント` 等**词级映射命中 11 行注释**;
- 受害例: `数据层重构`→`数据層重构` · `UI 层 filter`→`UI 層 filter` · `渲染层排版`→`渲染層排版` ·
  `词层 15 词合并`→`词層 …` · `12 鐵律 Pillar 标准`→`… 標準` · `六大主营分类选购指南`→`六大主营分类選び方指南`（**语义被破坏**）
- 发现方式: 波 4 写盘后**逐行对比 HEAD** 排查「注释行是否被改动」——**这是唯一能发现它的手段**（门童看不见）

**规则 (强制)**:
1. 任何**批量文本替换**（尤其字级/词级）**必须显式跳过注释行**（`//`、`/* */`、`*` 开头的 JSX 块等）;
   注意: 「跳过注释」在自然语言文本里同时能**减少误伤**, 不应作为可选项。
2. 替换后必须跑**「注释行 vs HEAD 逐行对比」**断言: 注释行改动数必须为 **0**（除非本批目标就是改注释）。
3. 单字级规则（如 `层`→`層`）**风险最高** —— 优先升格为词级规则; 无法升格时必须在**值作用域内**替换（不可全档无差别）。
4. 与门童 #16 的 `content` 字段盲区同族: **「门童看不见的地方」既是污染藏身处, 也是误伤重灾区**。

# ⚠️【置顶·2026-09-19 四条技术债】——「验收信号本身可能是假的」

> 2026-09-19 K3 裁决 2 登记。**共同主题: 判据/信号失效 ⇒ 执行层在假事实上做决策。**
> 本条与下方「饱和上限」同族: 前者是**计数被钉住**, 本条是**判据/链路在说谎**。
> **一句话铁律: 任何「✅ 通过」都必须先证明该判据自己能失败 (阴性对照), 再采信它的通过。**

## 技术债 1 — remote 别名跟踪 ref 陈旧, `git status` 谎报「本地 = 远端」

**模式**: 同一仓库配多个 remote 别名 (`origin` / `origin_ssh`, 实为同一 GitHub 仓库),
各自 `.git/refs/remotes/<alias>/main` 独立跟踪。任一别名**长期不 fetch**, 其跟踪 ref 即冻结在旧提交。

**事故 (2026-09-19)**:
- `origin_ssh/main` 冻结在 `e0fb2ed1` (2026-09-18 19:02)
- 真实远端头 = `f5bb90b6` → 后 `ee0e0164` (由 `origin` 通道推送)
- `git status` 输出 `main...origin_ssh/main [ahead 35]` ⇒ **误判「有 35 个 commit 从未推送」**
- 实际当时远端与本地差 0–1 个 commit

**处置 (强制)**:
1. 判断「推没推」**只认** `git ls-remote <remote> refs/heads/main` 或 `git fetch` 后的 `origin/main`;
   **禁止**用 `git status` 的 ahead/behind 下「推送是否成功」的结论 (它只反映**所跟踪的那个别名**)。
2. 多别名长期存在 ⇒ 必须收敛为一个 (或每次判断前强制 `git fetch --all`)。
3. 派活书/报告凡写「已推」, 必附 `git ls-remote` 返回的**真实 hash**。

## 技术债 2 — 「push ✅ + CI SUCCESS ✅」是假信号

**模式**: `git push` 的**成功**与「**我这次改动**上线」之间没有必然关系:
- push 可能把**别的** commit 推上去 (自己的 commit 晚于 push 动作完成);
- CI 绿的可能是**另一个 commit** 触发的 build。

**事故 (2026-09-19, 1-B 落点修复 `a5e14d37`)**:
- 上次成功 push 在 `08:19:11`, 止于 `f5bb90b6`;
- `a5e14d37` 提交时间 `08:19:20` —— **比 push 晚 9 秒**, 从未离开本机;
- 当时记录写「push ✅ + CF SUCCESS ✅」, CF 绿的实为 `cb73f581` (1-B 的**内容** commit,
  落在**未渲染**的 `page.tsx` 上, 正是原缺陷本身);
- 结果: 客户线上连续 2 小时看到的仍是旧口径, 而执行层以为已闭环。

**处置 (强制)**: push 生效的**唯一**判据 = ① `git ls-remote` 确认真实头 == 本地 HEAD
② **精确字符串探针**在线上命中 (不用通用词)。两者缺一, 不得写「已上线」。

## 技术债 3 — 门童 #16 (GSC 泄漏) 的「五类静默失效」——扫描器说 0 命中, 不代表没有

**性质**: 2026-09-19 Step B 判决性实验确证。**原假设「命中躺在存量基线里被豁免」被证伪** ——
`check-regression-guard.js` 的基线通道只对 `common.js:53 QUOTE_RULES` 内 **10 个品牌/i18n 规则 ID** 生效,
`GSC_LEAK_CUSTOMER_VISIBLE` **不在其中**; 且实跑 `guard.scan([该档])` 返回 `[]` (**命中从未生成**, 不是被扣减)。
真正的性质是**五类静默失效叠加**:

| # | 失效类 | 机制 | 实测证据 |
|---|--------|------|----------|
| ① | **字段盲区** | `scanTs()` 只扫 `title\|description\|excerpt\|keywords` + 多行段落数组; **`content:` (客户可读正文大头) 完全不在扫描面** | `buying-guides.ts` L929/930/931 三语尾巴**都被正则命中**(繁 3 / 简 3 / 日 2 处), 但 `scan()` = **0 命中** |
| ② | **引号截断** | 提取正则 `['"]([^'"]{20,})['"]` 以引号为边界; 客户 HTML 正文天然含引号(`class='…'`) ⇒ 捕获被截断且常因 `{20,}` 被整条丢弃 | 同一泄漏串: 无引号 → **3 命中**; 包进含 `class='…'` 的 HTML → **0 命中** |
| ③ | **双引号看空** | `(['"])([^'"]+)\1` 对 `"value"` 匹配成 `""` (值=空) ⇒ 双引号写法整体看空 | `blog-posts.ts` **30 条** / `sku-seo-data.ts` **170 条**双引号值长期未被扫 |
| ④ | **文件级漏覆盖** | `CUSTOMER_VISIBLE_FILES` 缺少 `src/data` **最大的两个档** | `products-content.ts` **1,195 KB**(含 4 处活跃泄漏) / `sku-seo-data.ts` **1,138 KB** 均不在名单 |
| ⑤ | **词汇级漏覆盖** | 正则「枚举措辞」: 只收简化字与特定搭配 | `GSC データ`(日文片假名) / `imps 數據`·`pos 數據`(纯词不邻接数字) / `校準報價`·`校準來源` / `拍板日` / `§0.23` —— 全部 **0 正则覆盖** |

**后果 (2026-09-19 实测)**: 补面后从「0 命中」变为 **7 处真实活跃泄漏**:
- `products-content.ts` L51/52/3203/6566 — 客户可见定价表含内部口径(`校準報價`/`校準來源`/`真實校準`/`1.3 倍合理利潤`/`RMB→HKD 1.087`);
- `category-seo-content.ts` L4552/4653 — 客户可见 `description` 写「**K3** 真實身份 ≤ 2 小時回覆」(内部代号泄漏)。

**处置 (2026-09-19 已落地)**:
1. `scanTs()` 重构为**解析式提取器**: 字符级扫描 `'…' / "…" / \`…\`` 三种字面量, 先取整值, 再按「键 + 花括号栈外层字段」判所有权; 空键/locale 键归外层字段; 无法判定 ⇒ `content` (**保守照扫**)。
2. 覆盖名单补入 `products-content.ts` / `sku-seo-data.ts`。
3. 正则补 8 条: 日文片假名变体、`imps/pos + 數據/数据/データ` 纯词形态、`數據誠信紅線`(须含「誠信」)、`校準報價/來源/錨點`、`真實校準`、`拍板日`、`§0.xx`。
4. JSON 路径补**行号定位**(原恒报 `line:0` ⇒ 报告不可执行); 同一处命中按 `(文件,行,规则,命中词)` 去重。
5. 注入回放 **12 例 PASS / 0 FAIL**, 且**含阴性对照**(干净文案 / 含 class 属性 / `色彩校準`行业词 / 注释行引用) —— 对照组自身先被验证。

**规则 (强制)**:
- 凡报告「✅ 0 命中」, **必须同时声明扫描面**(扫了哪些文件 / 哪些字段 / 哪些引号形态); 缺此声明的「0」不构成证据。
- 扫描器/提取器的**注入回放用例必须含**「值内含引号」「值内含 HTML 属性」「双引号值」「多行模板串」四种形状, 且必带阴性对照。缺此用例的扫描器视为**未验证**。
- 补扫描面会**暴露存量真值**, 必须**补面单独一刀 + 先出全量清单**, 清理另批 —— 否则「真值暴露」与「修复」混在一次 commit 里无法验收。

## 技术债 4 — 修复型「危险写入」必须逐次替换, 且计数断言要覆盖**全部出现次数**

**模式**: `String.replace(oldStr, newStr)` 传字符串参数时**只替换第一处**。
若同一串在文件里出现 N 次 (如表格表头 ×2 / 单元格 ×10), 只替 1 处 ⇒ **半截修复**;
表面「替换完成」, 实际残留 N−1 处。

**事故 (2026-09-19 Step B-7)**: 首版脱敏脚本用 `out.replace(oldS, newS)` 单次替换,
表头「校準來源」×2 与单元格「2026-07-18 參考實詢」×10 **只各替了 1 处**。

**为什么没酿成事故**: 三件套的**形状断言**(改后 token 必须 0 残留) 当场拦下并**拒绝写盘**。
⇒ 这正是 §12「只查计数的守卫是假守卫」的反面教材: **计数断言 + 形状断言缺一不可**。

**规则 (强制)**:
1. 批量文本改写**禁止**用 `String.replace(str, str)`; 用 `split(old).join(new)` 或按断言次数**循环替换**, 并**复查残留必须为 0**。
2. 计数断言必须写明**期望次数**(不是「≥1」), 且改后要**再断言一次残留数 = 0**。
3. 脱敏/改写类脚本必须附加**守恒断言**: 例如「价格数值序列与百分比序列逐位一致」——
   证明只动了口径、没动业务数据。(2026-09-19 Step B-7 即以此断言通过验收)

## 技术债 5 — 正则 `[^'"]` 型「静默失败」的共同特征: 不报错、不告警、报告写 ✅

**共性**: 技术债 ①–⑤ 全部**没有抛错、没有告警**, 汇总行显式打印「✅ 0 命中」,
执行层据此宣布「已清零」, 而真相是「根本没看见」或「看错了」。

**规则 (强制)**: **静默失败比报错更危险**。任何「✅ 通过」的报告, 必须能回答:
**「这条判据怎样才能失败? 我有没有跑过它失败的样子?」**(= 阳性/阴性对照)。
答不出来的通过, 视为未验证。

## 技术债 6 — 门禁的 `fix` 文案是「给人看的建议」, 不是「给机器用的替换串」

**模式**: 门禁规则的 `fix` 字段若包含**具体可复制的成品文案**, 下游 remediation 可能把它当**字面替换值**落盘。
本次事故中, **门禁的修法建议反过来成了污染源**。

**事故 (2026-08-18 ~ 09-01, 2026-09-19 结案)**:
- `credibility-guard.js` `CRED_HEIDELBERG` 的 fix 写 `改用 "进口印刷设备" 描述`;
- `sop10-guard.js` `SOP10_HEIDELBERG_6_1` 的 fix 写 `改用 "进口印刷设备"`;
- 同期 remediation (如 `be744435` 全站 508 处硬数据撤除) 撤除品牌名 (`Heidelberg` / `HP Indigo`) 时,
  **采用了 fix 建议里的中文串**作为替换文本, 并在**三语一起**做了全局替换。

**后果 (2026-09-19 实测)**: `進口印刷設備` 共 **109 处** —— zh-hk 48 处**正常**(繁体中文语境),
**en 40 处 + ja 21 处 = 61 处为污染**, 形态如 `German 進口印刷設備 presses`(en) / `進口印刷設備 6+1 機台プルーフ`(ja)。
计入门童 #4 `I18N_POLLUTION_EN` 的为 **240 字符**, 占 Step E 术语表 778 字的 **31%**。

**为什么当时没拦住 (两段根因, 缺一不可)**:
1. fix 文案含可直接落盘的成品文案, 且**未标注「示例, 勿直接替换」**;
2. **当时没有任何 locale 守卫** —— 门童 #4 双向化 (`I18N_POLLUTION_EN`) 建于 2026-09-19, 在此之后。

**规则 (强制)**:
1. 门禁的 `fix` 字段**不得包含可直接落盘的成品文案**; 如需示例必须显式标注「**示例, 勿直接替换**」。
2. 任何**替换类**操作必须有**目标语系守卫** (往 en 值写中文 / 往 ja 值写简体, 都必须被拦)。
3. 术语归一化必须**一次拍板、三语分别取值**, 禁「一个中文串三语通投」。

# ⚠️【置顶·最高优先教训】门禁的「饱和上限」会伪装成「稳定的红线」

> 2026-09-19 K3 Step 3.5 固化。**凡门禁有截断/上限机制，报告必须给出未截断的真实计数。**

## 事故
`scripts/guards/common.js` 的 `scanRule()` 原实现：
```js
if (count >= MAX_HITS_PER_RULE /* =50 */) break;   // ← 直接 break
```
⇒ 超出 50 的部分**从未被扫描、从未被计数**。汇总行显示的「50」/「51」是**上限饱和值**，不是真实命中数。

## 后果（两条都很贵）
1. **真缺陷量级完全不可见**：price-data 90 处 + 全站页脚简体等真缺陷长期被「50」遮住，
   执行层连续多轮据此向 K3 汇报「red 51 → 50，基线可下修 1」——**该结论是饱和伪影，不是真实归因**。
2. **「修了却没动」看起来像没修**：修完污染后数字仍在 50（被钉住），第一轮误判为「修复未生效」。

## 修法（2026-09-19 已落地）
- `common.js`：**扫描不再 break**，只**截断明细**（`count >= MAX` 时 `continue` 而非 `break`），
  真实命中数另计并登记 `SCAN_STATS`；导出 `getScanStats()` / `resetScanStats()`。
- `check-regression-guard.js`：汇总后输出
  `📊 真實計數 (未截斷): <rule>=<n> | …` 与
  `⚠️ 明細截斷 (真實命中 > 保留上限 50): <rule> 真值 N / 僅保留 M`。
- 默认 `src/` scope 实测：汇总 red 仍为 **2**（修法不改变判定），但真实计数暴露：
  `CRED_4_PLUS_NUMBER 真值 3783 / 僅保留 716`、`SOP10_4_PLUS_NUMBER 3783/716`、
  `I18N_META_LENGTH 820/296`、`CRED_ISO_9001 706/355`、`CRED_SELF_FACTORY 260/54`、
  `CRED_HEIDELBERG 232/213`、`BRAND_JA_ALTERNATE 77/66`。
  ⇒ **此前多轮报告的「🟠 1555 / 1562」同样是截断值**，真实量级为 2–5 倍。

## 规则（强制）
1. 任何门禁/扫描器的报告**必须区分**：`真实计数` vs `已保留明细数`；有上限者必须显式标注「明細已截断」。
2. 上限只能限制**输出体积**，**绝不能限制计数**。
3. 「红线数字长期不动」本身就是**异常信号**，须先查是否有上限/豁免/基线把数字钉住，再谈「没有恶化」。
4. 同一族反例：门童 #20 的专用基线（存量只许递减）是**合法**的钉住机制（语义明确、可递减排空）；
   而 MAX_HITS_PER_RULE 是**非法**的钉住（无语义、永远不动、掩盖增量）。

## 待办（本次未覆盖，属同一族）
- `scripts/guards/brand-guard.js:78` 与 `scripts/guards/i18n-guard.js:229` 各自**另有一套 `break` 上限**，
  未经 `common.scanRule` ⇒ 其规则的真实计数**仍可能被截断**，须同法改造。

### 规则 TSC_ERROR_COUNT_DROP_IS_A_RED_FLAG — tsc 错误数**下降**是危险信号, 不是改进 (2026-09-18 内容落地事故)

**事故形态**: 落地 zine 新篇时, 用脚本把 `const lpZine...: BlogPostMeta = {...};` 声明
插到了**数组字面量内部**（锚点选错 —— `  lpPackagingBoxPrice2026,\n  ];` 位于
`export const blogPosts: BlogPostMeta[] = [` **之内**）→ TypeScript 语法错误。

**★ 最危险的表现**: 重跑 `npx tsc --noEmit`，错误数从**基线 54 掉到 2**。

```
修复前: TSC error lines: 54   ← 基线
破坏后: TSC error lines: 2    ← ★ 看起来"大幅改善", 实际是语法错误导致 tsc 早停
                                    只报 2 条 parse 错误, 全部类型错误被掩盖
修复后: TSC error lines: 54   ← 恢复基线才算对
```

**为什么危险**: 基线守则写的是"tsc 持平"。若把**下降**也当成通过（"54 → 2，比基线还好"），
就会放过一个**整个文件解析失败**的破坏 —— 这正是"用指标代替判断"的典型翻车。

**触发条件**（任一命中即需停下核对）:
- tsc 错误数 **少于**已记录基线（尤其断崖式下降）
- 错误里出现 `TS1xxx`（语法/parse 类）—— 基线错误全是 `TS2xxx` 类型错误
- 单文件错误消失但未做任何类型相关修改

**修复模式 (可复用)**:
1. **结构性插入的锚点必须在目标结构之外**：要往 `const arr = [ ... ]` 里加一项，
   声明块插到 `const arr = [` **之前**，数组内**只**加标识符
2. **锚点唯一性断言不够，还要断言"锚点相对结构的位置"**：本次锚点确实唯一，但位置错了。
   新增断言：`indexOf(声明块) < indexOf('export const blogPosts')`
3. **插入后必须验证"行级 diff 只有新增 + ≤1 变更行"**（本次两版都过了这条，
   说明纯行级 diff **无法**发现"新增内容插错位置" —— 必须叠加结构断言）

**机审建议**: 把"tsc 错误数 == 基线"作为硬断言（不是 `<=`），并在 CI/门童里标注
基线错误全部为 `TS2xxx`；出现 `TS1xxx` 一律视为结构破坏。

**同批教训（§12 三件套有效性再证）**: 该脚本的**前置计数断言**（锚点唯一 + 名称未注册）
全部通过、**行级 diff 断言**也通过 —— 是事后 `tsc` 才暴露。说明
**三件套必须包含"语言级可解析性"这一维度**（JSON 文件用 `JSON.parse`，TS 文件用 `tsc`/`tsx`）。

### 规则 HREFLANG_FALSE_ALARM_MEASUREMENT_BUGS — 探针自身三个 bug 造出「全站缺 hreflang」假警报 (2026-09-18)

**事故形态**: 我用 curl 探针统计 `<link rel="alternate" hreflang=...>`，得出「17 条路由中 13 条缺
hreflang」，并已准备按此开通全站修复。**该结论是错的 —— 是探针 bug，不是站的 bug。**

**三个独立 bug（叠加）**:

| # | bug | 后果 | 修法 |
|---|-----|------|------|
| 1 | 正则写小写 `hreflang=` | Next.js 服务端渲染成 **camelCase `hrefLang`** → 全部漏统计 | HTML 属性大小写不敏感，一律 `/hreflang=/i` |
| 2 | 一次突发 51 请求（17 路由 × 3 locale，间隔 250ms） | 中途被限流 / 降级返回短响应 → 记成「0 命中」 | 串行 + 间隔 + **校验响应确为目标页** |
| 3 | 未校验响应体 | 把失败响应当成「该页真的没有」 | 不合格响应标 `INVALID`，**不计入 0** |

**决定性反证**: 单独抓同一 URL 连续 6 次 → 计数恒为 4、HTML 长度恒为 183979 B（完全确定性）；
而突发审计脚本对**同一 URL** 报 0。**同一目标两次测量结果不同 ⇒ 先怀疑测量，再怀疑系统。**

**★ 根本教训**: **「测得 0」与「真的没有」是两件事。**
任何「缺失类」结论（缺 hreflang / 缺 schema / 缺 canonical / 缺翻译）动手修之前必须过三道自检：
1. **匹配口径**：大小写 / 属性顺序 / 引号形态 / 转义是否覆盖真实渲染结果？
2. **响应有效性**：状态码 + 长度下限 + 页面 marker 三重校验，不合格判 `INVALID` 而非 `0`
3. **确定性**：同一目标重复抓 3-6 次结果一致，才可作为结论依据

**本次可信结论（单独验证）**: home / category / product / blog 列表 / blog 正文 / guide
**均正确输出 4-6 条 `hrefLang` 链接（含 x-default）**。全站是否存在 hreflang 缺口**尚无可信结论**，
须按三重校验重跑审计 —— **不得据假警报开工**。

**同源教训**: 本 turn 两次翻车（`TSC_ERROR_COUNT_DROP_IS_A_RED_FLAG` 与本条）都是
**指标本身错了**，不是系统错了。凡「指标给出惊人结论」时，先验证指标。

### 规则 SAFECOMMIT_ATOMIC — 非原子提交 = stage 污染 (K3 2026-09-19 评估, 立即生效)

**事故形态（2026-09-19 本会话实测两次）**：多会话并发改同一仓库时，
`git add` 与 `git commit` 之间的窗口会被别的会话/车道**插入 staged 文件**：
- 事故 1：本批 commit 带进并发会话的 `scripts/gen-p0-title-batch.mjs`（当作**删除**提交）；
- 事故 2：本批 commit 带进并发会话 staged 的 `scripts/guards/guard-manifest.json`（同样当作删除）。
两次都改了别人的产物，只能事后 `git checkout HEAD --` 补回。

**修法（原子提交，不依赖人的纪律）**：

```bash
# ✅ 正确: add 与 commit 在**同一条命令**内完成 —— 中间没有窗口给并发会话插入
git commit -F .hermes/_commit-msg-<batch>.txt -- <path1> <path2> ...
# （tracked-but-gitignored 的台账文件需先 `git add -f <path>`，再走上面的原子形式）

# ❌ 反例: 先 git add a b c，再 git commit -m "..."   ← 两次事故的形态
# ❌ 反例: git commit -a / git add -A → 必然吞掉并发会话的全部改动
```

**旁路配对规则（与门童 #22 配套，强制）**：凡不得已使用 `--no-verify`，
必须**同时**设置唯一入口环境变量（不靠记忆写 footer）：

```bash
ZP_BYPASS_REASON="<为什么必须绕过>" git commit --no-verify -F <msgfile> -- <paths...>
node scripts/guards/bypass-audit-guard.js --stamp     # 理由自动落 .hermes/regression-guard/bypass-audit.jsonl
```

**判据（自检三问，提交前必答）**：
1. 我 `git commit` 带的 pathspec 是否**逐一列明**？（`-a` / `-A` / 无 pathspec 一律否）
2. `git diff --cached --name-only` 是否**只剩我这批**的文件？（有别人的 ⇒ `git reset -q` 重来）
3. 若用了 `--no-verify`，`ZP_BYPASS_REASON` 是否已设？（未设 ⇒ 台账记 `UNATTRIBUTED`，pre-push 门童 #22 会拦）

**为什么不能只靠「先 reset 再显式 add」**：那仍是两步、仍有窗口，且**依赖人每次都记得**。
原子形式把正确做法变成**一条命令**，错误做法才是需要多打字的那个 —— 与「bypass 入口要 awkward」同一设计原则。

**同族规则**: `BYPASS_UNATTRIBUTED`（旁路留痕）· `RULE_TRANSLATION_MISSING`（治理机制失效）

### 规则 LOCATE_BEFORE_PATCH — 未 dump 真实文本就定位条目 = 盲修 (K3 2026-09-19 入档)

**事故形态**: print-specs × 3 补 FAQ 时出现 1 处五要件越界 (zh-hk Q4 答案 55 字 / 首句 13 字)。
我连续 **4 轮**打补丁去修 **Q5 (DPI/出血)**, 而真正越界的是 **Q4 (數碼 vs 柯式)**
—— 自检读数一直是对的, 错的是**我没先 dump 真实文本就下手定位**。

**与 DOUBLE_METHOD_RECOUNT / SEG9_FAQ_FORMAT 的关系**: 三者同源 (先取真实样本再动手), 场景不同 ——
  · SEG9_FAQ_FORMAT: 写**正则**前先 dump 一条真实样本;
  · LOCATE_BEFORE_PATCH (本条): 修**条目**前先 dump 该条目的真实文本与独立计数;
  · 共同根因: 在确认目标条目的真实文本前, 任何修补都是盲目的; 反复打补丁只烧 token, 不消除越界。

**修法 (三步, 不可省)**:
1. **dump 真实文本**: 直接打印目标条目的完整字符串 (不入正则、不凭记忆);
2. **分开打印「读到的文本」与「算出的数」**: 使计数口径与被数对象同时可见 —— 才能发现「数的是另一条」;

### 规则 STALE_REMOTE_REF_FALSE_BACKLOG — 未 fetch 的 remote-tracking ref ⇒ 积压计数是假读数 (K3 2026-09-20 指定入档)

**事故形态**: 连续两轮向 K3 报告「**59 / 71 个 commit 未推送**」，并据此提出 push 前的 5 项 verify 与三段验证方案。
实测：`git fetch` 后 `origin/main...HEAD = 0 0`，且 `origin/main == origin_ssh/main == HEAD == 34a6910e`
—— **根本没有积压，push 是 no-op**。

**根因**: 用 `@{u}..HEAD` 计数，而 `@{u}` 指向 `origin_ssh/main` —— 该 remote-tracking ref
**从未被 fetch 过**，git 一直在与一个**过期快照**比较。量具本身未校准，读数却当成了阻塞依据。
（另: 两个 remote 的 URL **完全相同**（`git@github.com:zprintprohk-rgb/zprintpro.git`），故「推错目标」风险亦不存在。）

**为什么属本族**: 与 `METRIC_INTEGRITY_FIVE_TRAPS` 同源 —— **被测量的不是仓库，而是本地缓存**。
这是第 6 种系统性陷阱：**远端状态读数陷阱**。

**修法 (三步, 不可省)**:
1. **任何 push/积压结论前，先 `git fetch <remote> main`**；禁止直接读 `@{u}` 或任何未 fetch 的 ref。
2. **用 `git rev-list --left-right --count origin/main...HEAD` 复算**，并要求与 `@{u}..HEAD` 交叉一致；
   两者不一致 ⇒ **先查量具**（哪几个 remote？各自 URL？ref 是否新鲜？）。
3. **多 remote 时先 `git remote -v` 比对 URL**：URL 相同即同一仓库，不存在「推错目标」；
   不同才需 K3 裁决生产目标。

**危害边界（诚实记录）**: 本次**未造成损坏** —— 反而因「先修后推」的保守判断而**避免了一次空操作 push**。
但两轮错误报告**污染了 K3 的决策前提**（整份 push 方案建立在虚构的 59 条积压上），
代价是 K3 一轮规划成本。属于「量测错误导致的决策污染」，与 §0.23.2 红线同性质。

**同族规则**: `METRIC_INTEGRITY_FIVE_TRAPS`（本族母规则, 本条为第 6 种）· `DOUBLE_METHOD_RECOUNT`（母规则）· `TIME_READING_UNVERIFIED`（同属「读数未复算」）· `HREFLANG_FALSE_ALARM_MEASUREMENT_BUGS`（同源：量具自身 bug）

交叉验证对象 = **提交树**（对照 `git show --stat HEAD`）。

### 规则 HOOK_SSOT_ACTIVE_DIVERGENCE — 门童 hook「SSoT 有」不等于「git 真的读到」(2026-09-20 固化两次同族事故)

**事故形态**: 门童 hook 存在**两份档**，语义不同但外表相似：

### 规则 POWERSHELL_OUTPUT_ENCODING — PowerShell 输出重定向写出 UTF-16LE，下游按文本处理即错 (K3 2026-09-20 入档)

**事故形态**: 用 `node scripts/X.cjs 2>&1 | Tee-Object -FilePath out.txt` 落盘证据 dump，
git 把该文件判为 **`Bin 0 -> N bytes`**（二进制），随后 `check-encoding.js` 报 **CRLF 57 行 / 27 行**。
若非编码门禁拦截，该「证据」会以二进制形态入库 —— **不可 diff、不可 grep、不可 review**。

**根因**: PowerShell 的 `Tee-Object` / `Out-File` / `>` **默认编码为 UTF-16LE**（含 `FF FE` BOM），
而本仓工具链（`check-encoding.js` / 文本门禁 / `rg`）**一律假定 UTF-8 LF**。
叠加第二层：`Out-String` 会把程序输出按 Windows 换行 **`\r\n`** 重建，于是同一个文件**同时**中两个陷阱。

**实测取证（本仓复算）**:
```
head bytes: ff fe 3d 0 3d 0        ← UTF-16LE BOM + "=="
git diff --cached --stat → ...txt | Bin 0 -> 4344 bytes
node scripts/check-encoding.js → ⚠️ CRLF: ...txt (57 lines with \r\n)   exit 1
```

**为什么属本族**: 与 `METRIC_INTEGRITY_FIVE_TRAPS` 同源 —— **被测量的对象在落盘那一刻已经变性**。
这是第 7 种系统性陷阱：**取证通道自身的编码陷阱**（前 6 种见各条）。
「工具输出的是不是文本」这件事**没有被验证过**，却被当成文本继续下游处理。

**修法（固化机制，非文字提醒）**:
1. **禁止**用 PowerShell 重定向落盘文本证据（`Tee-Object` / `Out-File` / `>`）。
2. **改用 Node 显式 UTF-8**：`fs.writeFileSync(path, content, 'utf8')`（无 BOM）。
   若必须留在 PowerShell，须 `[System.IO.File]::WriteAllText($p,$s,(New-Object System.Text.UTF8Encoding($false)))`。
3. **换行必须正规化**：写前 `.replace(/\r\n/g,'\n')`；否则 `check-encoding.js` 仍会拦。
4. **落盘后必自检三件**：`head` 前 3 字节无 `ff fe` / `fe ff`、`git diff --cached --stat` 不出现 `Bin`、
   `node scripts/check-encoding.js` exit 0。

**危害边界（诚实记录）**: 本次**未造成内容损失** —— dump 内容完整，且已被门禁拦下。
真实代价是**一次返工**（重新生成 + 换行转换 + 重新暂存）。
但若当时没跑编码门禁，入库的将是**无法 review 的二进制证据**，会把「有证据」变成「有假证据」。

**同族规则**: `METRIC_INTEGRITY_FIVE_TRAPS`（母族，本条为第 7 种）· `DOUBLE_METHOD_RECOUNT`（同源：单来源未交叉验证）· `COMMIT_MSG_OVERCLAIMS_TREE`（同属「记录与实际不一致」）

**配套**: `scripts/check-encoding.js`（机器判据）· AGENTS.md §8 第 7 条（Python 写文件必须 `newline='\n'`，本条为其 PowerShell 侧对应）

### 观察记录 COMMIT_TIMESTAMP_ANOMALY — commit 的 `%ad` 与实际调用时刻不一致（待观察，未升级为规则）

> **级别**: 🟡 **观察**（非确定规则）。按 K3 2026-09-20 指示：先记录，若再现同类案例再升级为 `error-patterns` 规则。

**观察对象**: commit `9330f96b`（本会话提交）。

**现象**: 本会话记录「`git commit` 调用后，`git log -1` 首次读到 `%ad = 18:02:28`」，
而**当时系统时钟读数早于该值**（该次取证 `Get-Date` 为 `18:01` 量级）。
即：**提交时间戳比读取时刻还晚**，初见像「时间戳在未来」。

**排查结论（排除项）**: ① 无 `amend`；② 无 `reset`（`git reflog` 该 commit 仅一条 `commit:` 记录）；
③ 无外来作者（`%an` = 与其余 commit 同一身份）；④ `parent` 正确（= `885d03d9`，与预期一致）；
⑤ 内容正确（9 文件 / 427 insertions，与 `git diff --cached --name-status` 暂存集完全一致）。

**当前判定**: **未解释**。最可能为**取证时序**而非时钟异常（`git commit` 实际完成时刻略晚于该次 `git log` 取证），
但**未能复现亦未能证伪** → 按「不解释就不下结论」记录。

**为何值得记**: 与 `TIME_READING_UNVERIFIED` 同族 —— **时间读数需双源交叉验证**。
本条的教训价值在于：**当时间戳与直觉冲突时，先怀疑取证时序，不要直接怀疑仓库被篡改**（后者会导致错误的「历史被改写」告警）。

**升级条件**: 再出现 1 次同类现象（时间戳晚于读取时刻且排除 amend/reset）→ 升级为规则并给出判据。

### 规则 SELF_REPORT_METRIC_DISAGREEMENT — 自报指标与复算不一致时，先查输入通道再怀疑工具 (K3 2026-09-20 入档)

**事故形态**: 复算 `disposable-menus/en` 标题当量时，**手打字符串**经 `equiv()` 得 **46**，
而 `verify-menus.cjs` 从**文件实测**读同一标题得 **49** —— 差 3，且**三个不同 title 上都稳定差 3**
（`Disposable Menus | Free Shipping $99+ | ZprintPro` 等）。
稳定偏移最像**工具 bug**，第一步极易误判为「当量函数处理 `$`/`+` 有缺陷」。

**真相**: **工具没错，是我的输入被 shell 改写了**。
该字符串经 `node -e "…"`（PowerShell 双引号内传参）时 **`$99` 被 PowerShell 当作变量展开**，
实际传给 `equiv()` 的不是文件里的字符串。改用**从文件读取**的复算器 `verify-menus-equiv.cjs` 后，
读数与 `verify-menus.cjs` **逐字一致**（49/46/51/54 全部吻合）。

**判据（关键区分）**: **稳定偏移 ≠ 必然工具 bug**。稳定偏移有两种成因：
① 工具确定性错误；② **输入通道确定性改写**（shell 展开 / heredoc 展开 / 引号规则 / 编码转换）。
后者**更常见**，且伪装成前者。

**修法（固化机制，非文字提醒）**:
1. **凡复算「文件里的值」，必须从文件读** —— 禁止手打目标字符串传给量具。
   （正式化工具：`scripts/verify-menus-equiv.cjs`，按 `readFileSync` + 切片取值）
2. **两法不一致时，先 dump 输入而非怀疑量具**：打印 `len` / 非 ASCII 字符及码位，
   一眼即可看出「我传进去的字符串」与「文件里的字符串」是否同一串。
3. **PowerShell 传参给 node 时**：`$` 会被展开 → 用**单引号**或 `-e` 内避免 `$`，
   或直接走文件/`fs` 读取。
4. **交叉验证对象是「同一个输入」**：若两次复算的输入来源不同（手打 vs 文件），
   则两者不一致**不能作为工具 bug 的证据**（per `DOUBLE_METHOD_RECOUNT`：双方法必须在**同定义域**）。

**危害边界（诚实记录）**: 本次**未造成错误结论落地** —— 疑点被拦在提交前，最终 4 处修复全部基于文件实测值。
真实代价是**一次额外排查**（写了一个新复算器）。
若当时直接信「46」而补 +4，会把标题改成**超出必要长度**的版本（50→53），
并顺带误记一条「当量工具 bug」的假规则。

**同族规则**: `DOUBLE_METHOD_RECOUNT`（母规则，本条补其隐含前提：**同定义域**）·
`METRIC_INTEGRITY_FIVE_TRAPS`（同源：指标本身错）· `LOCATE_BEFORE_PATCH`（同源：先取真实文本）·
`POWERSHELL_OUTPUT_ENCODING`（同属「PowerShell 通道改写数据」）

**配套**: `scripts/verify-menus-equiv.cjs`（从文件读取的复算器）· AGENTS.md §0.23.2 三闸门（第 1 条：匹配口径，先 dump 真实样本）· 技能 `zprintpro-self-evolution-hardening` §五

### 规则 WORKSPACE_DIRTY_OVERFLOW — 工作区脏文件堆积到「git status 不再是可靠信号」 (2026-09-20 立)

**事故形态**: 2026-09-20 实测 `git status --porcelain` 共 **599 条**（绝大多数是 `.hermes/` 下的
**未追踪备份目录 + 生成报告**：`_bak-*` / `_archive-*` / `_probe-*` / `reports/*.json`）。
单条无害，**堆到三位数后性质改变**：

| # | 风险 | 具体后果 |
|---|------|----------|
| 1 | **真实改动被淹没** | 599 条里找「我这轮改了哪 3 个档」只能靠 grep 过滤，人眼必漏 |
| 2 | **掩盖并发会话的改动** | 另一车道的未提交改动混在同一噪声里 → 无法快速察觉 → §0.35.7 撞车的温床 |
| 3 | **「干净」判据失真** | 收尾信号（无 `MM` 且 staged 删除归零）本就只是**单点快照**；叠加脏噪声后更难分辨「真完成」与「中途暂停」 |
| 4 | **备份目录被误当资产** | `_bak-*` 与正式产物同前缀，易被误 commit（本仓已发生「`_` 前缀交付物游离在版本控制外」，见 `COMMIT_MSG_OVERCLAIMS_TREE`） |
| 5 | **push 前盘点失效** | 「可推清单」靠人工核对；脏树越大越容易漏看**不该推的那个档** |

**判据（机器可检，不靠人眼）**:
- `node scripts/audit-workspace-dirty.mjs` —— 三分分类，**只读，绝不删档**：
  A 已追踪未提交（**真实改动，最需要看**，含「生成物」子标）／B 未追踪·建议 `.gitignore` 或需人工判断／C 未追踪·疑似可删（备份/坏档/一次性探针）
- **阈值告警**: `--threshold <N>` → 未追踪条数超阈即 `exit 1`。
  实测定基线 **599**（2026-09-20），此后**只许递减**。

**修法（顺序不可颠倒：先量 → 再分类 → 最后才动）**:
1. **先量化并落盘**（脚本产出 `.hermes/reports/workspace-dirty-audit.json`）——不许凭印象说「差不多干净」。
2. **分类结果交 K3 裁决**：进 `.gitignore` / 正式入库 / 删除，**执行层不擅自删**。
   （本项目已发生过「一方清理扫掉另一方 staged 变更」，per §0.35.7）
3. `.hermes/_bak-*` / `_archive-*` 一律进 `.gitignore`（它们是**备份**，不是交付物）。
4. 正式脚本**不带 `_` 前缀**（见 `COMMIT_MSG_OVERCLAIMS_TREE`「附带纠正」）。

**为什么属本族**: 与 `HOOK_SSOT_ACTIVE_DIVERGENCE` 同源 —— **「以为的状态」与「实际的状态」偏离，
且偏离本身不产生任何报错**。前者是「以为有门禁」，本条是「以为工作区干净」。

**同族规则**: `HOOK_SSOT_ACTIVE_DIVERGENCE`（同源：静默状态失真）·
`SAFECOMMIT_ATOMIC`（同机制：以「说的」代替「实际的」）· `METRIC_INTEGRITY_FIVE_TRAPS`（母族）

**配套**: `scripts/audit-workspace-dirty.mjs`（三分分类 + 阈值告警）· AGENTS.md §0.35.7（人手会话并发锁双条件）
