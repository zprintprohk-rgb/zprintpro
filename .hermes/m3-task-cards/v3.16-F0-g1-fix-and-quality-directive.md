### 四条硬 SOP（对应 P1-P4 问题模式）

**SOP-1 红灯冻结令（治 P1，权重最高）**
- verify-deploy 返回 failure 的瞬间：停止一切编辑与 push，包括"和失败无关"的任务。
- 唯一允许的动作: ① 根因调查（只读）; ② 1 段报告 K3; ③ 等拍板。
- 收到拍板后只允许执行拍板内容本身，不允许"顺手带"其他任务上同一班车。
- 自检句式（每次 push 前默念）: "上一次 verify 是绿的吗？"

**SOP-2 阈值二元化（治 P2）**
- 所有验收项表述只有两种: `✅ 达标 (实测值 X ≥ 阈值 Y)` 或 `❌ 未达标 (实测值 X < 阈值 Y)`。
- 英文 snippet 阈值牢记: 130-160 **词** ≈ 700-900 **字符**；中日文 130-160 字 ≈ 200-280 字符。单位混淆 = 验收无效。
- 未达标不是罪，**软化未达标才是罪**。未达标 + 明确补救计划 = 不扣分；措辞掩盖 = 双倍扣分。

**SOP-3 根因 diff 优先法（治 P3）**
- 任何 build/运行时异常，第一动作永远是: `git show --stat <sha>` + 与最近一个绿色版本 diff，列出**全部结构差异**（新 import、新目录、缺导出、配置文件改动），按差异排序候选根因。
- 机制猜测（"可能是因为 SSR 渲染冲突"）只能排在结构差异之后，且必须标注"未经 diff 排除"。
- 每个候选根因后面必须写: **验证方法**（怎么确认/排除它）。没有验证方法的候选不许写进报告。

**SOP-4 债务熔断（治 P4）**
- 每版本最多延后 2 个任务，第 3 个 = 砍范围（明确写"本版本不做"），不写"延后"。
- 同一任务连续 2 个版本被延后 → 第 3 版本**强制第一优先执行**（T27 FAQPage JSON-LD 已达此线，v3.16 必须完成）。
- 版本开工第一段先列: 上版本债务清单 + 本版新增清单 + 熔断检查结论。

### 即时生效的三条措辞禁令

1. 禁 "勉强达标 / 基本达标 / 差不多" → 只允许 达标 / 未达标。
2. 禁 "等 K3 拍板" 之后继续动手 → 说了等就是等，手离开键盘。
3. 禁 报告里出现未附验证方法的根因猜测。
