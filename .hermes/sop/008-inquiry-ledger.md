# SOP 008 · 询盘轻量计数台账（4 字段版）

> **状态**：K3 2026-09-04 12:39 拍板，从原"询盘归因台账"降级为**轻量询盘计数器**。
> **红线**：成交全走扫码/转账/线下，**没有任何在线支付闭环**，AI 无法自动知道月进账。
> 因此本台账**只数询盘条数与来源，不记金额、不记成交、不做营收归因**。营收/复购由 K3 人脑 + 银行流水感知，AI 不装能度量。

---

## §1 这个台账回答什么、不回答什么

| 问题 | 本台账能否回答 |
|---|---|
| 这周/这个月来了多少条 WhatsApp 询盘？ | ✅ 能 |
| 询盘主要从哪个页面/渠道/语言来？（?text=#src= 参数） | ✅ 能 |
| 询盘集中在什么品类？（盒/贴纸/海报/校园/烫金…） | ✅ 能 |
| 询盘大概要多少量？（数量分布，判断 B2B/B2C） | ✅ 能 |
| SEO 流量到底有没有带来询盘？ | ✅ 能（条数趋势 + 来源） |
| 一个月进账多少？成交率？复购率？营收归因？ | ❌ **不能，也不做**（无在线支付，扫码/转账不可自动归因） |

**北极星口径调整**：原 v3.3 §5 把 008 台账当作"B2B 复购 50% 北极星"的度量基础设施——该定位作废。B2B 复购与营收靠 K3 人工感知；本台账只服务"SEO/GEO 有没有带来询盘"这一个可自动度量的问题。

---

## §2 只记 4 个字段

每条询盘一行，**只填这 4 项**，多一个字段都不加：

| 字段 | 取值 | 来源 |
|---|---|---|
| `src` 来源 | WhatsApp 链接 `?text=#src=xxx` 参数里的来源标记；无参数记 `direct` | 询盘消息/链接自动带 |
| `客户` | 客户昵称/公司名（WhatsApp 显示名即可，不需真实隐私信息） | 人工一句话 |
| `品类` | 包装盒 / 贴纸 / 海报 / 校园教育 / 烫金 / 纸袋 / 名片 / 其他 | 人工一句话 |
| `数量` | 客户报的数量（如 500 个 / 1000 张 / 200 份）；未报记 `未报` | 询盘内容 |

**禁止记录**：成交金额、付款方式、是否成交、客户电话/地址等隐私、利润率。

## §3 存储与更新

- **文件**：`data/inquiry-counter.json`（轻量 JSON，一份就够，不搞复杂数据库）
- 结构：

```json
{
  "updatedAt": "2026-09-05",
  "inquiries": [
    { "date": "2026-09-05", "src": "zh-hk-blog-packaging-box", "customer": "Wong 生 / XX 茶行", "category": "包装盒", "qty": "1000 个" }
  ]
}
```

- **更新方式**：K3 或运营每收到一条 WhatsApp 询盘，花 10 秒追加一行；也可由 K3 每周口述"这周来了 N 条，大概品类"，由 M3 汇总。
- **不做**自动成交回填、不做金额字段、不做漏斗转化率计算。

---

## §4 怎么用这个数据（唯一用途）

1. **周报里看趋势**：询盘条数周环比、来源分布（哪个 Pillar/语言/渠道带来的）、品类分布。
2. **验证 SEO 动作**：某 Pillar 改完 7-10 天验证窗后，看对应 `src` 来源询盘有没有抬头——判断内容/排名动作是否真带来生意线索。
3. **B2B vs B2C 判断**：看数量分布（上千个=B2B 框架单，几十几百=B2C 散单），指导内容重心。
4. **仅此而已**。营收、成交、复购不进 AI 报表，K3 自己心里有数即可。

---

## §5 与门童/流程的关系

- 本 SOP **不设门童**、**不阻塞 push**、**不进 12 铁律**。它只是一个可选的轻量记录习惯。
- 询盘来源参数 `?text=#src=` 的埋点由内链/CTA 组件负责，台账只消费、不改组件。
- 若连续 2 周无人记录，不追责、不报警——它是辅助，不是 KPI 枷锁。
